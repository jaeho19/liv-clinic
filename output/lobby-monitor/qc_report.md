## 5. 깜빡임(스트로브) 검사 — 통과 (①편 검수에 없던 항목)

**왜 넣었나.** ④편 1차 출고본에 `t=52.07~58.03`의 **97프레임 약 7.5Hz 스트로브**가 그대로
인코딩돼 있었다(`lru_cache`가 돌려준 PIL 이미지에 매번 덧그린 결함). `freezedetect`와
`blackdetect`는 **원리상 이걸 못 잡는다** — 두 검사 모두 프레임 간 변화가 **모자란** 쪽을
찾는데, 이 결함은 변화를 **늘리는** 방향이기 때문이다. 스틸 표본도 비켜 갔다.

**방법.** 최종 MP4를 전수 디코딩해 인접 프레임 MAD를 전부 잰다(표본 아님). `MAD > 5.0`인
쌍을 추린 뒤 **위치로 1차 분류**한다 — `render_frame`의 디졸브 창이 `XF=12`, 즉 블록 경계
기준 `[b−6, b+5]`이므로 경계 ±6프레임은 정상 전환으로 본다. 경계 밖 스파이크는
**`MAD(n,n+2) / MAD(n,n+1)` 비율**로 판별한다. 한 방향 전환(페이드·슬라이드·크로스페이드)은
두 칸 건너뛰면 차이가 더 커져 비율 > 1이고, 왕복 스트로브는 두 칸 뒤에 원래 그림으로
돌아와 비율 < 1이 된다. 블록 경계는 검수 코드에 베껴 두지 않고 장면 모듈 소스를 AST로
읽어 쓴다 — 좌표를 베끼면 소스가 바뀌어도 검수는 옛 기준으로 통과한다.

## 6. 지표 상호간섭 — "0건 세 개"만으로는 부족하다

④편에서 **결함 두 개가 서로를 가리고 있었다.** 캐시 오염 스트로브가 H06 정지 클립의
freeze를 덮어 `freezedetect`가 0건을 보고했고, 스트로브를 고치자 `freeze_start 54.133 /
3.167초`가 드러났다(라이브 창에도 켄번즈를 걸어 해결). 즉 **freeze 0건은 "정지가 없다"가
아니라 "정지를 가릴 만큼 다른 게 움직인다"일 수도 있다.**

이번 검수의 음성·양성 대조군에서도 같은 성질을 실측으로 확인했다 — 스트로브를 심은 클립은
`blackdetect`·`freezedetect`를 **통과한다**(10절).

그래서 이 리포트는 "세 지표가 0"으로 끝내지 않는다.

- 깜빡임은 별도 지표(인접 MAD + 왕복 비율)로 본다 — 5절.
- 각 지표의 판별력을 결함 주입으로 확인한다 — 10절.
- 그래도 자동 검사만으로는 부족하므로, **16분 한 바퀴를 사람이 한 번은 끝까지 본다**를
  현장 확인 항목에 넣었다 — 16절 6번.

## 10. 검수의 판별력 — 일부러 망가뜨린 입력으로 확인

모든 항목이 PASS로 나오는 검수는 검수가 아니라 장식일 수 있다. 그래서 같은 함수에 결함을
심은 입력을 먹여 **실제로 FAIL이 나오는지** 확인했다.

| 검사 | 정상 입력 (PASS 기대) | 결함 주입 (FAIL 기대) | 결과 |
| --- | --- | --- | --- |
| 깜빡임 | ②편 95~99초 4초 → PASS (MAD 최대 0.079, 스파이크 0) | 다른 두 프레임을 30fps로 교대 4초 → **FAIL** (스파이크 120, 왕복 의심 119, 비율 최솟값 0.0) | 판별함 |
| 표본 휘도 + `blackdetect` | PASS | 앞 2초 완전 암전 → **FAIL** (어두운 표본 4개, 최저 평균 휘도 0.00, black 1건) | 판별함 |
| `freezedetect` | PASS | 스틸 1장을 5초 고정 → **FAIL** (freeze 1건) | 판별함 |
| 고정 크롬 | PASS | 하단 로즈 필을 검은 박스로 덮음 → **FAIL** (필 위반 8개) | 판별함 |
| QR | 정상 12.5초 → PASS | QR 일부를 흰 박스로 가림 → **FAIL** (6지점 전부 빈 문자열) | 판별함 |
| **(교차 확인)** `black`/`freeze` | — | **깜빡임을 심은 클립** → **PASS** | 6절의 근거. 두 지표는 깜빡임을 원리상 못 잡는다 |

이 대조군이 `qc_check.py`의 실제 결함도 하나 잡았다: 마지막 인접쌍이 스파이크일 때

## 15. 보고 — ①편도 같은 기준이면 정지 구간 2건에 걸린다

이번 검수의 합격선(3초 이상 완전 정지 0건)을 ①편 〈리프팅 시티〉에 그대로 적용해
직접 측정했다.

```
$ ffmpeg -i LIV_lifting_city_01_1080x1920_6min_silent.mp4 -vf freezedetect=n=0.001:d=3 -an -f null -
freeze_start: 219.7        freeze_duration: 3.000000    freeze_end: 222.7
freeze_start: 318.033333   freeze_duration: 3.133333    freeze_end: 321.166667
$ blackdetect  ->  0건
```

- **①편은 이미 납품·검수 통과 상태이고 이 작업 범위 밖이다.** 다시 렌더하라는 뜻이 아니다.
- 다만 ①편 `qc_report.md` 3절의 "freezedetect(n=0.001, d=3): 검출 0건"은 **사실과 다르다.**
  같은 절이 "2.5초 기준으로는 5구간(최장 3.13초)"이라고 적었는데, 3.13초짜리 구간이 있으면
  d=3에서도 반드시 잡힌다. 같은 PC·같은 ffmpeg(9.0)로 d=2.5는 5건, d=3은 2건이다
  (무음 AAC 트랙 버전도 같은 2건).
- 두 구간 다 **카드 3장이 세로로 놓인 안내 화면**이다(219.7초 "피부 상태 · 고민 부위 · 이전
  시술", 318.0초 "신경 쓰이는 부위 · 이전에 받은 시술 · 원하는 변화"). 조판이 고정되고 배경
  켄번즈가 x264 양자화 아래로 내려가 3초 남짓 완전히 멈춘다. 즉 2~3초 멈춘 듯 보이는 구간이
  6분짜리 ①편에 두 곳 있다는 뜻이고, **16분 루프를 걸면 그 두 곳이 반복된다.**
- 판단은 사장님 몫이다. 고친다면 ②③④편이 쓴 방법(`KB_RATE`를 0.009로 올려 배경 이동량을
  키운다)을 ①편 렌더러에 적용해 재인코딩하면 된다. 그림은 바뀌지 않는다.

   사람만 보는 화면이 아니다. 불편하다는 반응이 나오면 그 구간의 사진만 교체하면 된다.

## 18. 기술 부채 (다음 작업으로 넘기는 구조 문제)

### 18-1. `_bg_clip` 계열이 세 편에서 갈렸다

배경(생성 클립 → 블러 앰비언트 플레이트) 전환 헬퍼가 **세 편 모두 다르다.**

| 편 | 함수 | 차이 | 당시 이유 |
| --- | --- | --- | --- |
| ② | `_bg_clip(key, t, cut, ...)` | 원형. 라이브 프레임 감광은 fix round 1에서 인자로 추가 | — |
| ③ | `_bg_clip(key, t, cut, ...)` | 명시적 키워드 인자, `int(t*FPS)+1` 인덱스, `z1` 선계산 | `**kw` 오타가 조용히 기본값으로 렌더되는 문제를 막으려고 |
| ④ | `_h06(t, run)` + `_live_to(amb, t, cut, dim)` | 앰비언트를 블록이 아니라 전역 시각으로 잇고, 라이브 창에도 켄번즈를 건다 | 배경이 H06 하나뿐이라 블록마다 부르면 같은 6초가 5번 돈다 |

각자 정당한 이유가 있었고 그래서 세 갈래가 됐다. **최종 상태는 공용 모듈(`liv_video/`)에
하나를 올려 세 편이 같은 헬퍼를 쓰는 것이어야 한다.** ④편의 요구(전역 시각 + 라이브 켄번즈)가
가장 넓으므로 그쪽을 일반화하고 ②③편 호출부를 옮기는 순서가 맞다. 옮긴 뒤에는
`test_toolkit_parity`와 같은 방식으로 **옮기기 전 프레임과 픽셀 동일**을 확인해야 한다.

### 18-2. 파리티 테스트의 골든 프레임이 리포에 없다

`edit/tests/test_toolkit_parity.py`는 ①편 렌더러에서 `liv_video` 툴킷을 뽑아낸 뒤에도
결과가 픽셀 단위로 같은지 보는 회귀 가드다. 그런데 비교 기준인 골든 6장
(`output/lifting-city/edit/golden/t*.png`)은 `output/.gitignore`의 `*/edit/golden/` 규칙으로
**추적하지 않는다.** ①편 커밋 `8a2eeae`에서 들어온 기존 바이너리 미추적 정책이고 이번 작업이
만든 문제가 아니다.

- 이 PC에는 6장이 있어 테스트가 돈다(오늘 112 passed에 포함).
- **새로 클론한 환경에서는 스킵이 아니라 에러가 난다.** 이 파일에는 `skipif` 가드가 없고,
  픽스처가 `subprocess.run(..., check=True)`로 ①편 렌더러를 돌린다. 폰트(`*/edit/fonts/`)와
  전처리 에셋(`*/edit/prep/`)도 추적하지 않으므로 렌더 자체가 실패한다.
- 재생성은 아래처럼 한다. **반드시 툴킷 추출 이전 버전(`8a2eeae`)으로 만들어야 한다** — 지금
  코드로 다시 만들면 "지금 코드 = 지금 코드"를 비교하는 무의미한 테스트가 된다.

```bash
cd D:\dev\LIV_homepage
# 파일 위치로 경로를 잡으므로(EDIT = dirname(__file__)) 반드시 같은 폴더에 풀어야 한다
git show 8a2eeae:output/lifting-city/edit/render_video.py > output/lifting-city/edit/_render_pre.py
cd output/lifting-city
python edit/prep_assets.py            # 원본 사진·폰트가 먼저 있어야 한다
python edit/_render_pre.py --stills 0.5,45,123,190,265,354 --out edit/golden
rm edit/_render_pre.py
```

**이 절차를 실제로 돌려 확인했다** — `8a2eeae` 렌더러로 다시 만든 6장이 지금 PC에 있는
골든 6장과 **최대 화소 차이 0**으로 같다. 즉 현재 골든은 툴킷 추출 이전 결과가 맞고,
위 명령으로 그대로 복구된다(확인 후 임시 파일은 지웠다).

### 18-3. 이 검수 도구 자체의 한계

- 깜빡임 검사 임계는 인접 MAD **5.0**이다. 화면 전체가 매 프레임 평균 5/255(약 2%) 왕복하는
  정도다. ④편 실제 결함은 최대 10.96이라 걸렸지만, 그보다 약한 깜빡임(화면 일부만 미세하게
  흔들리는 경우)은 이 임계에 안 걸린다. 임계를 더 내리면 정상 전환이 대량으로 딸려 들어온다
  — 세 편의 경계 밖 최대 MAD가 각각 7.65 / 7.31 / 6.96이다.
- 고정 크롬 검사는 2fps 표본이다. 한 프레임만 깨진 결함은 지나칠 수 있다(렌더러 쪽
  `test_chrome_present_in_every_sampled_frame`이 별도로 본다).
- `copy_guard`는 리터럴 대조다. 한계는 16절 4번에 적었다.
