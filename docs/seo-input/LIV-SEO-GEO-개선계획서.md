# LIV 클리닉 SEO·GEO 개선 실행 계획서

작성일: 2026년 9월 8일 · 대상: https://liv-clinic.net/ko

**목표:** 검색과 AI 답변에서 LIV의 시술·의료진·방문 정보를 정확하게 발견하도록 개선하고, 적합한 방문자의 상담 신청을 늘린다.

**구현 방향:** 기존 URL과 디자인을 활용해 구조 → 콘텐츠 → 기술 → 배포 검증 순서로 개선한다. 병원 정보·가격·의료 근거의 원본을 먼저 확인하고, 본문과 검색용 데이터가 같은 원본을 사용하게 한다.

**기술 환경:** 공개 페이지에서 Next.js 관련 표식이 관찰되었으나, 저장소·버전·CMS·배포 환경은 확인하지 않았다. 실제 파일 경로와 명령은 코덱스가 프로젝트를 연 뒤 확정한다.

**참고 자료:** 사용자가 제공한 [에이브랜치 실행 키트](https://a-branch.com/useful-info/seo-geo-ai-prompt-execution-kit)의 프롬프트 1~4 전문을 검토해 단계 구분, 사실 검증, 기존 구현 보존, 배포 전 검증 원칙을 반영했다. 이번 산출물은 실행 계획이며, 사이트 수정이나 배포는 수행하지 않았다.

## 1. 권장 전략과 범위

LIV는 홈페이지, 시술 상세, 가격, 의료진, Q&A, 다국어 페이지를 이미 갖추고 있다. 따라서 우선순위는 **정보의 일관성 → 핵심 시술 페이지의 근거와 설명 → 검색 접근 검증 → 상담 전환 측정**이다.

시장 우선순위에 대한 별도 답변이 없는 상태이므로, 한국어 사이트의 국내 고객 유입을 우선하고 해외 고객은 기존 언어 페이지의 품질을 점검하는 것으로 계획했다. 실제 상담·매출·검색 데이터를 확보하면 1주 차에 우선 언어와 시술을 조정한다.

| 접근 방식 | 장점 | 부담 | 판단 |
|---|---|---|---|
| 기존 페이지를 개선하고 중요한 설명만 확장 | 기존 검색 자산과 디자인을 활용, 빠르게 검증 가능 | 운영 사실과 의료 근거 확인 필요 | **권장** |
| 모든 언어·시술의 콘텐츠를 동시에 확장 | 넓은 범위를 다룰 수 있음 | 번역·검토·유지 비용 증가 | 핵심 템플릿 검증 후 진행 |
| 사이트 전체 리뉴얼 | 설계 자유도가 높음 | URL·전환 흐름·운영 안정성 부담 | 현재 공개 점검만으로 필요성 확인 안 됨 |

첫 구현 범위는 한국어 핵심 페이지와 공통 템플릿이다. 핵심 시술은 사이트에서 강조하는 울쎄라피 프라임·써마지 FLX·실리프팅을 후보로 두되, 실제 운영 우선순위로 확정한다. 매출 순위나 검색량이 높다고 확인된 것은 아니다.

## 2. 공개 사이트에서 확인한 현황

### 2.1 이미 갖춘 요소

- 홈페이지와 확인한 시술·의료진·의료정보 페이지에 고유한 제목과 설명, 자기 URL을 가리키는 canonical이 있다.
- 홈페이지와 여러 상세 페이지에 11개 언어 및 x-default 연결이 있다. 한·영 울쎄라 페이지는 서로 연결되는 hreflang과 각 언어의 canonical을 확인했다.
- 병원·웹사이트 구조화 데이터가 있고, 페이지에 따라 BreadcrumbList, MedicalProcedure, MedicalWebPage, Physician, FAQPage 등이 이미 출력된다.
- 울쎄라 상세에는 가격표, 비교표, FAQ와 관련 시술 연결이 있다.
- 의료정보에는 25개 Q&A가 있고, 확인한 답변에는 짧은 답과 상세 설명, 관련 시술 링크가 있다.
- 가격 안내에는 부가세 별도 및 상담 후 최종 비용 결정 조건이 표시된다.

새 기능으로 일괄 재작성할 대상이 아니라, 정확성과 작동 범위를 점검할 기존 자산이다. 확인 대상: [홈페이지](https://liv-clinic.net/ko), [울쎄라](https://liv-clinic.net/ko/lifting/ulthera), [의료정보](https://liv-clinic.net/ko/medical), [가격](https://liv-clinic.net/ko/pricing), [의료진](https://liv-clinic.net/ko/about/staff).

### 2.3 아직 판단할 수 없는 항목

- 실제 Google·네이버·Bing 색인 범위와 검색 유입, 상담 전환율.
- 전체 라우트의 HTTP 상태, 리다이렉트, X-Robots-Tag, 크롤러별 응답.
- robots.txt·sitemap.xml의 실제 원문과 운영 CDN/WAF 정책. 이번 도구 접근에서 확인하지 못했으므로 파일이 없거나 봇을 차단한다고 판단하지 않는다.
- 초기 HTTP HTML과 최종 DOM의 차이. 일부 첫 읽기에서 Loading 표시 후 본문이 확인됐지만, 이것만으로 CSR 전용 또는 색인 실패라고 판단하지 않는다.
- Core Web Vitals, 모바일 실사용 성능, 모든 언어의 번역 품질.
- 의료진 자격·연수·장비 인증·시술 수치·가격의 최신 원본.

## 3. 검색 의도와 페이지 역할

다음은 실행 우선순위를 정하기 위한 후보 질의다. 검색량 수치를 확보하지 않았으며, ‘검색량이 많다’는 의미가 아니다.

| 사용자 목적 | 후보 질의 | 우선 URL 또는 페이지 | 다음 행동 |
|---|---|---|---|
| 병원 확인 | 리브성형외과, 리브 김수영 | /ko, /ko/about/staff | 의료진·진료 내용 확인 |
| 가까운 시술 병원 찾기 | 신사역 울쎄라피 프라임, 신사역 써마지 | 기존 시술 상세 | 가격·방문 방법·상담 |
| 예산과 조건 비교 | 울쎄라 가격 샷 수, 써마지 600샷 가격 | /ko/pricing와 해당 시술 | 포함 항목 확인 후 상담 |
| 시술 선택 | 울쎄라 써마지 차이 | /ko/medical의 기존 답변 및 선택적 상세 가이드 | 두 시술의 상세 안내 |
| 실리프팅 이해 | 압토스 실리프팅, 실리프팅 종류 차이 | 기존 /ko/lifting/thread부터 확인 | 제품·범위·주의사항·상담 |
| 방문 준비 | 리브성형외과 주차, 신사역 리브 위치 | /ko/about/location | 길찾기·예약 |
| 해외 방문 준비 | Ultherapy Seoul, LIV Clinic English consultation | 기존 영문 시술·외국인 진료 안내 | 언어·일정·비용 확인 |

비교 질의의 공개 검색 결과에서는 병원의 비교 칼럼과 표 형식 설명이 관찰됐다. 따라서 LIV에서도 비교를 찾는 사람에게 충분한 선택 기준을 제공하는 것이 합리적이다. 이는 페이지 형식에 대한 관찰이며, 경쟁사의 의학적 주장을 근거로 채택한 것은 아니다. 관찰 예: [시크릿성형외과 비교 칼럼](https://www.secretps.com/columnskin/view/18737), [오드의원 비교 칼럼](https://blog.odeclinic.co.kr/ulthera-vs-thermage-comparison).

코덱스 실행 시에는 실제 Search Console 자료와 대표 질의 3~8개의 결과를 다시 확인해 이 표를 조정한다. 검색어의 지역명·어순만 바꾼 페이지를 여러 개 만들지 않는다.

## 4. 단계 0 — 원본과 기준 상태 확보

**예상 기간:** 1~2일. **담당:** 코덱스·개발 담당자, 병원 운영자.

1. 프로젝트 루트, 지침, 패키지 관리자, 라우트, 콘텐츠 원본, 배포 설정을 확인한다. 외부 CMS가 원본이면 저장소에 별도 원본을 만들지 않는다.
2. 현재 변경 사항을 확인하고, 정의된 lint·typecheck·test·build를 가능한 범위에서 실행해 기준 결과를 기록한다.
3. 공개 페이지와 관리자·문의 조회·개인화 영역을 구분한다. 공개 상담 안내와 개인 상담 내용은 별개로 취급한다.
4. 홈페이지·울쎄라·써마지·실리프팅·가격·의료진·의료정보·위치·상담·영문 대표 페이지를 점검 대상으로 확정한다.
5. 운영자는 병원명, 연락처, 도보 안내, 주차, 가격 조건, 실제 의료진·자격, 우선 시술의 최신 원본을 제공한다.
6. 검색·전환 도구에 접근 가능하면 최근 90일과 직전 비교 기간을 확보한다. 미연결이면 코드 분석과 공개 점검부터 진행한다.

**완료 기준:** 실제 파일과 콘텐츠 원본, 수정 범위, 기준 검증 결과가 식별됨. 실행하지 못한 항목은 ‘실행 불가’로 남긴다.

## 5. 단계 1 — 검색 기회·사이트 구조 개선

**참고 키트:** 프롬프트 1. **예상 기간:** 2~3일.

**수정 위치:** 실제 저장소에서 찾은 공통 header·footer·navigation, 시술 카드, Q&A 관련 링크, breadcrumb, 상담 CTA 연결 컴포넌트.

### 작업 S1. 페이지별 역할과 이동 흐름 정리

- 홈페이지는 병원·주요 진료·의료진을 이해하는 출발점으로 둔다.
- 시술 상세는 해당 시술의 설명과 상담 판단을 담당한다.
- 가격은 조건을 비교하는 기준 페이지, 의료정보는 질문을 해결하는 허브로 둔다.
- 의료진·장비·위치는 신뢰와 방문 준비를 돕고 시술 페이지에서 연결한다.

권장 흐름은 `의료정보 ↔ 시술 상세 ↔ 가격 → 상담`이며, 의료진·위치로도 문맥에 맞게 이동할 수 있어야 한다. 기존에 잘 연결된 링크는 유지한다.

### 작업 S2. 현재 링크의 목적을 명확히 하기

- consult-prep로 이동하는 링크가 상담 준비 도구라면 ‘상담 준비하기’처럼 목적을 알린다. 시술 정보를 찾는 사람에게는 해당 안내 페이지 링크도 제공한다.
- ‘의료정보 더보기’만 있는 곳은 가능한 경우 관련 질문 또는 상세 가이드로 직접 연결한다.
- 가격표의 시술명에서 해당 시술 상세로 이동할 수 있도록 한다.
- 모바일에서도 핵심 메뉴·관련 페이지·상담 연결을 사용할 수 있는지 확인한다.

**완료 기준:** 우선 페이지가 메뉴·허브·관련 링크로 발견 가능하고, 수정한 내부 링크가 의도한 실제 페이지로 연결된다. 대표 main과 제목 구조가 명확하다. 신규 문서가 필요하면 목적과 필요한 자료만 정하고 빈 페이지는 만들지 않는다.

## 6. 단계 2 — 핵심 페이지 콘텐츠 개선

**참고 키트:** 프롬프트 2. **예상 기간:** 4~6일 + 의료진 검토 시간.

첫 묶음은 **울쎄라·써마지·실리프팅·가격·의료진의 최대 5개 페이지**로 제한한다. 다음 묶음에서 홈페이지와 의료정보의 중요한 답변을 확장한다.

**수정 위치:** 실제 CMS/콘텐츠 데이터, 페이지 본문과 title·description 문구, 가격 표시 컴포넌트, 작성·검토 정보 표시 영역. 구조화 데이터의 유형 재설계는 단계 3에서 한다.

### 작업 C1. 병원 정보와 가격의 기준 통일

- F01~F03의 원본을 확인하고 모든 노출 지점에 반영한다.
- 가격은 제품·부위·샷/줄/cc·횟수·부가세·마취 등 추가 비용·적용 기간·대상 조건을 구분한다.
- 동일한 가격표를 여러 곳에서 수동 복사하지 않도록 기존 데이터 원본을 재사용한다.
- 실제 가격 변경과 설명 개선을 구분한다. 운영자가 확정하지 않은 가격을 코덱스가 결정하지 않는다.
- 구조화 데이터나 메타 설명에도 운영 사실이 포함되어 있다면 본문과 불일치하지 않게 맞춘다.

### 작업 C2. 효과·인증·전문의 표현의 근거 확인

주장마다 `공개 문구 → 1차 출처 또는 운영 원본 → 적용 대상·범위 → 확인일 → 검토자`를 연결한다. 작업용으로 정리하되 새 기록 파일 생성을 모든 단계의 의무로 만들지는 않는다.

- ‘89%’, ‘110+’ 등은 해당 수치를 뒷받침하는 정확한 연구나 제조사 자료를 확인한다.
- 일반 장비군의 연구 결과를 특정 최신 모델 또는 LIV의 자체 성과처럼 표현하지 않는다.
- 허가·인증은 국가, 제품명, 적용 범위, 발급 주체를 구분한다.
- 특정 전문과목의 전문의라는 표현은 실제 담당자의 확인된 자격과 일치시킨다.
- 근거가 확인되지 않은 주장은 새 페이지·번역·JSON-LD에 확대 재사용하지 않는다.

이 계획서는 기존 표현의 위법 여부나 의료적 진위를 판정하지 않는다. 의료 내용과 광고 표현은 의료진·병원 담당자가 확인하고, 필요한 심의·법률 검토를 거친다. 검토 기준 자료: [국가법령정보센터 의료법 제56조](https://law.go.kr/법령/의료법/제56조).

### 작업 C3. 시술 페이지를 상담 판단에 유용하게 보완

이미 있는 가격표·비교표·FAQ를 활용하며, 페이지별 부족한 부분만 보완한다.

| 내용 | 작성 기준 |
|---|---|
| 첫 설명 | 시술의 목적과 상담에서 확인할 조건을 간결하게 안내 |
| 대상과 한계 | 고려할 수 있는 상황, 권하지 않을 수 있는 상황을 의료진 검토 후 설명 |
| 비용 | 확인된 가격과 적용 조건을 함께 표시 |
| 통증·회복·부작용 | 가능성과 개인차, 이상 증상 시 연락 방법을 함께 설명 |
| 비교 | 동일 기준으로 비교하고 일률적인 우열·효과 보장 피하기 |
| LIV의 운영 방식 | 실제 확인된 상담·정품 확인·시술·사후관리 절차만 사용 |
| 근거와 검토 | 중요한 주장 가까이에 출처, 실제 검토자와 검토일 표시 |
| 다음 행동 | 가격·의료진·관련 시술·상담으로 자연스럽게 연결 |

의료진 이름은 실제 검토가 끝난 문서에만 ‘검토자’로 표시한다. 특정 문장 길이나 FAQ 개수가 GEO의 필수 조건이라고 가정하지 않는다.

### 작업 C4. Q&A를 필요한 만큼 확장

현재 25개 질문을 전부 독립 페이지로 만들지 않는다. 기존 답변과 검색 의도를 대조해 다음 중 자료가 충분한 2~3개부터 확장한다.

1. 울쎄라·써마지의 차이와 상담에서 선택 기준을 확인하는 방법.
2. 실리프팅 제품·실의 수·범위에 따라 설명과 비용이 달라지는 이유.
3. 리프팅 상담 전 준비할 질문과 시술 후 연락이 필요한 상황.

독립 페이지가 필요한 경우에만 새 URL을 만든다. 기존 해당 문서가 있는지 저장소에서 먼저 찾고, 설명량이 적으면 기존 페이지의 섹션과 앵커로 해결한다. 새 문서에는 충분한 본문·출처·검토 정보·관련 링크를 갖춘 후 공개한다.

### 작업 C5. 제목·설명과 신뢰 페이지 보완

- 예시 방향: 울쎄라 페이지는 ‘울쎄라피 프라임 | 가격·시술 안내 | 리브성형외과’처럼 실제 제공 정보를 드러낸다. 확정 문구는 본문과 검색 데이터를 보고 선택한다.
- SCI 논문 수와 전체 논문 수는 범주를 명시하고 실제 목록으로 연결한다.
- Doctor Photo가 실제 자리표시자라면 확인된 사진으로 교체하거나 불필요한 자리표시를 정리한다. 생성한 인물을 실제 의료진 사진으로 사용하지 않는다.
- 언론·학회 활동은 정확한 원문과 날짜로 연결한다. 단순 노출 사실을 효과 검증이나 수상 경력으로 바꾸지 않는다.

**완료 기준:** 첫 묶음의 문구·가격·근거를 검토하고 반영함. 확인되지 않은 항목은 구체적으로 분리됨. 변경으로 기존 schema 사실 값이 틀려지면 해당 값만 최소 수정함. 전체 페이지를 획일적인 문체로 바꾸지 않음.

## 7. 단계 3 — 기술 SEO·AI 접근성 구현

**참고 키트:** 프롬프트 3. **예상 기간:** 3~5일.

**수정 위치:** 실제 metadata 생성부, sitemap·robots 라우트 또는 설정, JSON-LD 생성부, 언어 매핑, 페이지 렌더링, 이미지·스크립트 로딩. 기존 프레임워크 방식과 패키지를 우선한다.

### 작업 T1. 색인 가능성·대표 URL 검증

- 검색 대상 URL의 실제 HTTP 상태, robots meta와 X-Robots-Tag를 확인한다.
- canonical·내부 링크·sitemap에 같은 운영 URL 정책을 적용한다.
- 정상 페이지와 존재하지 않는 주소의 상태 코드를 구분하고, 기존 리다이렉트 체인·루프를 점검한다.
- sitemap에는 공개·정상 응답·색인 대상 대표 URL을 포함한다. 수정일은 의미 있는 실제 콘텐츠 변경을 반영한다.
- 관리자·개인 문의 조회는 별도 접근 정책을 유지한다. robots.txt는 개인정보 보호 수단이 아니다.
- preview의 의도적인 noindex를 유지하고 production에 섞이지 않게 검증한다.

robots 차단이나 의도치 않은 전체 noindex가 실제로 확인되면 해당 수정은 콘텐츠 작업보다 먼저 처리할 수 있다. 이번 공개 점검에서는 그런 장애를 확인한 것이 아니다.

### 작업 T2. 초기 HTML과 최종 화면 비교

홈·시술·Q&A·가격에서 초기 HTTP HTML과 브라우저 최종 DOM을 각각 검사한다. 제목·핵심 설명·가격 조건·관련 링크·Q&A 답변이 어떻게 전달되는지 확인한다.

아코디언이 접혀 있다는 이유로 검색 불가라고 판단하지 않는다. 답변이 HTML/DOM에 있는지, 클릭 후에야 별도 요청으로 처음 생성되는지를 구분한다. 검색에 중요한 본문이 상호작용에만 의존한다면 기존 프레임워크 안에서 필요한 범위만 서버/정적 출력으로 보완한다.

### 작업 T3. 다국어 연결과 번역 품질

- 가격 페이지의 HTML hreflang 부재를 다른 제공 방식과 대조하고 필요한 경우 보완한다.
- 존재하고 동등한 내용인 언어 페이지끼리 자기 자신을 포함해 상호 연결한다.
- 번역 페이지를 일괄 한국어 canonical로 합치지 않는다.
- 언어 전환 시 가능한 한 같은 시술·문서에 머물게 한다.
- 영문 설명과 한국어가 섞인 구조화 데이터의 의미가 일치하는지 검토한다.
- /en이 영어 사용자 전체를 대상으로 한다면 en-US만 쓰는 현재 정책을 재검토한다. 지역 코드를 기계적으로 제거하지 않는다.
- 11개 언어를 모두 확장하기 전에 실제 문의가 발생하는 언어부터 가격·의료진·사후관리 표현을 검토한다.

기준: [Google 언어별 페이지 연결 지침](https://developers.google.com/search/docs/specialty/international/localized-versions).

### 작업 T4. 기존 구조화 데이터의 정확성 개선

- MedicalBusiness/MedicalOrganization, WebSite, BreadcrumbList 등 기존 출력부터 검사한다.
- 의료진·병원·시술·문서의 관계를 실제 타입과 속성에 맞춰 연결하고, 중복·빈 값·샘플 값을 제거한다.
- 같은 병원이나 시술을 가리키는 언어 중립 @id는 사용할 수 있다. /ko가 없다는 이유만으로 ID를 전부 바꾸지 않는다.
- 실제 url·예약 action·문서의 canonical은 의도한 공개 페이지로 연결되어야 한다.
- datePublished·dateModified가 실제 이력인지 확인하고 요청일·배포일을 무조건 대입하는 구현이면 수정한다.
- 후기·평점을 임의로 생성하거나 자사 후기의 별점 노출을 약속하지 않는다. [Google 리뷰 구조화 데이터 지침](https://developers.google.com/search/docs/appearance/structured-data/review-snippet)을 적용한다.
- Schema.org 검증과 Google의 지원 검색 기능 검증을 구분한다. 모든 의료 schema가 Rich Results Test의 지원 대상은 아니다.

**최신성 주의:** Google은 2026년 5월 7일부터 FAQ 리치 결과를 표시하지 않으며, 6월에 관련 문서를 제거했다. 따라서 FAQPage 추가를 주요 성과 항목으로 삼지 않는다. 실제 FAQ 본문은 사용자에게 유용하면 유지하며, 기존의 올바른 schema를 단순히 표시 종료 때문에 반드시 삭제할 필요는 없다. 근거: [Google 공식 변경 이력](https://developers.google.com/search/updates).

### 작업 T5. 검색 봇과 학습 봇 정책 분리

- Googlebot·Bingbot·Yeti 및 목표 AI 검색 크롤러의 접근 가능성을 공식 문서와 실제 설정으로 확인한다.
- OpenAI의 검색용 OAI-SearchBot 접근과 학습용 GPTBot 정책을 구분한다. 검색 접근 개선을 이유로 학습 정책을 자동 변경하지 않는다. [OpenAI 게시자 안내](https://help.openai.com/en/articles/12627856-publishers-and-developers-faq).
- Claude·Perplexity 등은 실행 시점의 공식 문서로 이름·처리 범위를 확인한 후 필요할 때만 다룬다.
- robots 원문뿐 아니라 CDN·WAF의 실제 응답을 확인한다. 일반 브라우저 접근 성공은 모든 봇의 접근 성공을 증명하지 않는다.
- 기존 명시적 차단 방침과 충돌하는 변경은 별도 정책 결정으로 남긴다.

**llms.txt:** 기본 작업에 포함하지 않는다. Google은 이 파일을 검색 가시성·순위에 활용하지 않는다고 설명한다. 다른 실제 소비 시스템과 유지 목적이 있을 때 선택적으로 다룬다. 근거: [Google 생성형 AI 최적화 가이드](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide).

### 작업 T6. 모바일 속도와 상담 접근성

현재 점수는 미측정이다. 먼저 실제 사용자 데이터와 페이지별 측정으로 병목을 찾는다.

- 첫 화면 이미지, 영상·지도·외부 위젯, 이미지 크기, 폰트, 클라이언트 스크립트를 점검한다.
- 필요한 이미지 크기와 비율을 지정하고, 화면 밖 리소스의 지연 로딩을 검토한다.
- 프로모션 팝업과 하단 상담 UI가 본문·가격 조건·닫기 버튼을 가리지 않는지 모바일에서 확인한다.
- 성능 점수를 위해 핵심 기능이나 접근성 요소를 제거하지 않는다.

실사용 75백분위 목표는 LCP ≤ 2.5초, INP ≤ 200ms, CLS ≤ 0.1이다. 실험실 결과와 실사용 합격을 구분하고 표본이 없으면 ‘데이터 부족’으로 표시한다. 근거: [Web Vitals](https://web.dev/articles/vitals).

**완료 기준:** 우선 URL의 대표 주소·색인 지시가 충돌하지 않고, 실제 콘텐츠와 metadata·schema가 일치한다. 확인 가능한 렌더링·모바일 문제를 해결하고, 외부 계정이나 배포 후에만 검증할 항목을 분리한다.

## 8. 단계 4 — 배포 준비·최종 검증

**참고 키트:** 프롬프트 4. **예상 기간:** 1~2일.

이 단계에서는 새로운 개선 범위를 늘리지 않고 앞 단계의 회귀·빌드·배포 차단 문제를 해결한다.

| 검사 | 통과 기준 |
|---|---|
| 기존 검증 명령 | 실행한 lint·typecheck·test·build에서 이번 변경의 미해결 회귀 없음 |
| URL·상태 코드 | 우선 공개 페이지 정상 응답, 없는 주소 올바른 오류 응답, 루프 없음 |
| 색인·대표 주소 | 운영 URL·canonical·sitemap·robots 지시의 충돌 없음 |
| 본문·메타·schema | 수정한 가격·위치·자격·날짜의 사실 값 일치 |
| 다국어 | 실제 번역 페이지의 연결·대표 주소·언어 일치 |
| 사용자 흐름 | 모바일·데스크톱에서 관련 페이지와 상담 UI 사용 가능 |
| 범위·보안 | 사용자 변경 보존, 비공개 영역·환경변수·운영 데이터의 의도치 않은 변경 없음 |

‘통과 / 실패 / 실행 불가 / 해당 없음’을 검사별로 표시한다. 테스트 삭제, 검사 무력화, 성공하는 가짜 값 주입으로 통과시키지 않는다.

코드 연결 검사는 진행하되 실제 상담 접수·이메일·문자 발송은 부작용이 없는 테스트 환경 또는 별도 허용 범위에서 검증한다. 버튼 클릭과 실제 접수 성공을 혼동하지 않는다.

기본 종료 상태는 배포 준비까지다. 사용자가 해당 배포를 요청하면 기존 배포 대상·계정·환경을 확인하고 진행하며, 별도 요청 없이 commit·push·merge·deploy하지 않는다. 배포 후에는 robots → sitemap → noindex·canonical → 상태 코드·리다이렉트 → 검색 도구 처리 → 분석 이벤트·상담 흐름 순으로 확인한다.

## 9. 코드 외 운영 작업

### 로컬 검색 정보

- Google Business Profile, 네이버 스마트플레이스, 카카오맵의 병원명·주소·전화·시간·카테고리·공식 사이트를 대조한다.
- 이전 위치나 명칭이 현재 프로필과 혼동되는지 확인한다. 기존 리뷰와 장소 이력을 고려하고 임의로 새 프로필을 만들지 않는다.
- 웹사이트의 지도 링크가 정확한 병원 장소로 이동하도록 확인한다.
- 프로필 사진·진료 안내·예약 링크를 최신 운영 사실과 맞춘다.

Google은 로컬 결과에 관련성·거리·인지도를 활용한다고 안내한다. 이 계획에서는 직접 관리 가능한 정보의 정확성과 유용성을 개선한다. [Google 로컬 검색 안내](https://support.google.com/business/answer/7091?hl=ko).

### 검색 도구와 원문 콘텐츠

- Google Search Console·네이버 서치어드바이저·Bing Webmaster Tools의 소유 확인, 사이트맵 처리, 대표 URL 검사와 오류를 점검한다.
- 홈페이지의 Google 소유 확인 태그만으로 계정 접근·정상 등록·색인 완료를 판단하지 않는다.
- 네이버 블로그는 질문에 맞는 독립적인 설명과 병원의 실제 활동을 다루고 관련 홈페이지 안내로 연결한다. 같은 글을 기계적으로 복제하지 않는다.
- 의료진 영상은 필요한 경우 사이트에서 요약·자막·설명·관련 시술과 연결한다. 실제 존재하는 자료만 사용한다.

네이버 작업 기준: [네이버 서치어드바이저 가이드](https://searchadvisor.naver.com/guide/seo-basic-intro).

코덱스는 수정안·입력값 정리·검증을 도울 수 있다. 계정 소유 확인, 의료 원본 확인, 외부 프로필 게시 등은 실제 권한과 작업 요청 범위에 따라 담당자가 처리한다.

## 10. 일정·담당·성과 측정

### 권장 일정

개발 담당자 1명과 병원 검토자가 협업하는 경우의 초기 추정이며, 저장소·CMS·번역 상태에 따라 조정한다.

| 기간 | 주 작업 | 결과물 |
|---|---|---|
| 1주 차 | 기준 상태·운영 원본 확인, 단계 1 | 우선 URL 확정, 구조·내부 링크 개선 |
| 2주 차 | 단계 2의 첫 3~5페이지 | 검토된 본문·가격·근거·메타 문구 |
| 3주 차 | 단계 3 | 검색 접근·다국어·schema·렌더링 개선 |
| 4주 차 | 단계 4, 요청 시 배포, 외부 프로필 정리 | 검증 결과와 배포 후 확인 |
| 5~8주 차 | 데이터 관찰·Q&A 상세화 | 근거 있는 문서 2~3개, 제목·연결 개선 |
| 9~12주 차 | 언어·시술별 성과 비교 | 확장할 언어·콘텐츠·수정 우선순위 결정 |

의료진 검토가 늦어지면 그 내용의 게시만 보류하고, 독립적인 구조·기술 작업을 계속한다.

### 측정 방법

| 지표 | 수집·판독 방법 |
|---|---|
| 색인 범위 | 공개 색인 대상 URL 대비 실제 색인 URL을 확인. 제외 사유도 함께 기록 |
| 검색 유입 | 노출·클릭·CTR을 브랜드/비브랜드, 시술·언어·페이지로 구분 |
| Google AI 노출 | 최신 공식 문서가 안내하는 Search Console 생성형 AI 설정·성과 보고서의 계정 제공 상태 확인 후 사용 |
| AI 추천·인용 | 고정 질문에서 병원 언급과 실제 사이트 출처 링크를 별도로 집계 |
| AI 유입 | 확인 가능한 referrer·UTM으로 집계. 식별되지 않는 유입을 전부 AI라고 추정하지 않음 |
| 상담 행동 | 전화·카카오·예약 버튼 클릭은 보조 지표, 성공적으로 접수된 문의는 별도 지표 |
| 상담 품질 | 가능하면 운영 기록의 유효 상담·예약 확정·내원을 개인정보 없이 집계 |
| 페이지 경험 | 모바일/데스크톱 실사용 지표와 동일 조건의 실험실 비교 |

Google 관련 보고서와 설정은 최신 [공식 AI 가이드](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)를 기준으로 확인한다. 이번 조사에서는 실제 LIV 계정에 접근하지 않았으므로 보고서 활성화나 데이터 존재를 확인한 것은 아니다.

OpenAI는 ChatGPT 검색 유입에 utm_source=chatgpt.com을 사용한다고 안내한다. 이를 referrer와 함께 점검하되 모든 AI 유입이 관측된다고 가정하지 않는다. [OpenAI 게시자 안내](https://help.openai.com/en/articles/12627856-publishers-and-developers-faq).

분석 이벤트에는 이름·전화·이메일·상담 자유 입력·증상 같은 개인정보와 건강정보를 넣지 않는다. 의료 관련 상세 페이지·검색어가 외부 분석 도구에 어떻게 전송되는지도 기존 정책과 함께 점검하고, 허용된 비식별 집계부터 사용한다.

### AI 노출 표본 평가

실행 후보 질문 12~20개를 정해 월 1회 같은 언어·지역·검색 사용 조건으로 관찰한다. 첫 회에는 8~12개로 작게 시작해도 된다.

- 브랜드 확인: 리브성형외과 위치와 운영시간.
- 선택 도움: 신사역에서 리프팅 상담을 받을 때 확인할 점.
- 비교: 울쎄라와 써마지를 비교할 때 확인할 기준.
- 가격 조건: 울쎄라 샷 수와 견적을 비교하는 방법.
- 해외 준비: Seoul clinic consultation and aftercare for international visitors.

각 결과에 날짜·서비스·모델 표기(가능한 경우)·검색 여부·질문 원문·언급 여부·인용 URL·사실 오류를 기록한다. 전체 질문과 브랜드를 제외한 질문을 따로 집계한다.

`인용 관찰률 = LIV 사이트 링크가 인용된 유효 응답 수 ÷ 전체 유효 응답 수`

서비스 오류는 유효 응답에서 제외하고 실패 수를 별도 표시한다. 답변이 변동하므로 이 비율은 제한된 질문 표본의 관찰치이며 전체 AI 시장 점유율이나 고정 순위가 아니다.

### 목표 설정

개발 완료 목표는 우선 페이지의 확인된 불일치 해소, 내부 링크·색인 지시의 회귀 방지, 검증된 콘텐츠와 정상 상담 연결이다. 검색·AI 성과 목표는 첫 2주 기준 데이터를 본 뒤 정한다.

배포 전후 28일을 비교하고, 가능하면 전년 동기와 광고·프로모션 변화를 함께 본다. 노출은 늘었는데 클릭이 적으면 제목과 검색 의도를, 클릭은 늘었는데 상담이 적으면 조건·신뢰·상담 흐름을 우선 점검한다. 초기 데이터가 적으면 증가율보다 절대 건수와 개별 사례를 함께 본다.

## 11. 코덱스에 넘기는 방법

이 계획서와 별도 파일인 **LIV-Codex-실행프롬프트.md**를 실제 사이트 프로젝트에서 사용한다. 원본 코드가 없는 폴더에서 사이트를 새로 만들지 않는다.

1. 실제 저장소를 코덱스에서 열고 계획서를 첨부한다.
2. 실행 프롬프트 파일의 공통 조건과 1단계 블록을 먼저 실행한다.
3. 결과와 검증 상태를 확인한 뒤 2 → 3 → 4단계로 진행한다.
4. 운영자가 확인해야 하는 사실만 단계별로 확정한다. 독립적인 작업은 계속한다.
5. 실제 배포는 준비 결과를 확인한 후 별도로 요청한다.

각 실행의 최종 결과에는 상태, 최대 5개 변경 전후, 실제 변경 파일, 검증 결과, 미해결 문제와 다음 작업을 포함한다. ‘이미 올바르므로 변경하지 않음’도 근거가 있으면 정상 완료로 인정한다.

**이번 계획의 핵심 산출물:** 기존 페이지의 정보를 정확하게 맞추고, 병원의 검증된 설명과 근거를 연결하며, 그 결과가 검색·AI 시스템과 실제 방문자에게 일관되게 전달되는 구조를 만든다.
